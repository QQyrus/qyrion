Value loops

Close the loop with evidence.

One request carries the work from its source to a verified result. The agent composes only the capabilities the outcome needs, inside the scope you authorize.

  1. 1

    Trigger

    A story, bug, pull request, or code change.

  2. 2

    Context

    The desired outcome, environment, authorized actions, and a bounded run budget.

  3. 3

    Act

    Generate candidates and run web, mobile, or API checks with Qyrus.

  4. 4

    Verify

    Check terminal outcomes against the requirement. A failing check stays a failure.

  5. 5

    Evidence

    A requirement-to-evidence record, written back to the source when you allow it.

Generating a test, saving it, or queueing a run does not prove the objective. Every loop ends with verified outcomes, explicit failures, and the IDs of what it created.

Loop recipes

Seven starting points. Adapt them to your outcome.

The recipes are examples, not a closed list. Your connectors and permissions decide which steps are available.

Assurance loops run on the plugin's own capabilities, plus your work tracker connector for context and write-back.

A1Mobile quality

Acceptance criteria → candidate scenarios → real-device runs → authorized update.

ProofRequirement assertions with screenshots, video, and logs.

A2Web quality and export

A3API and contract

ProofActual responses and contract assertions.

A4Reproduce and verify a fix

Bug and environment → smallest reproduction → baseline failure → same assertions on the changed build.

ProofBefore and after evidence with build IDs.

A5Cross-channel journey

API setup → web action → mobile action → reconcile the shared state.

ProofCorrelation IDs and state transitions across channels.

A6Locator repair

Failing step and current page evidence → proposed replacement → original assertion validated again.

ProofBefore and after locator and a successful bounded rerun.

A7Pull request gate

Diff and intent → minimal impacted tests → run on the deployed build → permitted check or comment.

ProofTest mapping, outcomes, and build SHA. Merge authority stays separate.

Get started

You bring access. Your agent handles setup.

No prerequisite checklist to memorize. The bundled setup skill prepares missing tools and verifies the connections.

  1. 1

    Paste the setup prompt

    Use the request below in your coding agent. It obtains the public plugin and follows the included setup skill.

    Set up QyrusAI Assure from https://github.com/QQyrus/qyrion.

    Already installed? Say “Set up QyrusAI Assure.”

  2. 2

    Provide a private file path

    Create a local file with your Qyrus URL and X-API-Key. Give the agent its path when asked.

    Watch how to create your key ↓

  3. 3

    Confirm where to work

    Select your Qyrus team when prompted. Setup checks MCP access and Qyrion capabilities, and prepares the Python SDK.

    Reload the host if requested to load the installed plugin.

Prefer to install the plugin yourself?

Claude Code can install from the bundled public marketplace:

claude plugin marketplace add QQyrus/qyrion
claude plugin install qyrusai-assure@qyrusai-assure --scope user

Then say “Set up QyrusAI Assure.” If Claude requests it, run /reload-plugins or start a new session to load the skills and MCP server.

For Codex and Cursor, follow the host-specific installation instructions. The plugin identifier is qyrusai-assure.

Antigravity uses the same skills with its native plugin format. Follow the Antigravity setup instructions; setup registers the Qyrus MCP connection using your private key file. Verify loaded skills and MCP access in your host. Work-tracker connectors authenticate separately.

One key. Your Qyrus environment.

Create your X-API-Key

The same key connects Qyrus MCP, Qyrion sessions, and the qyrusai SDK. Use the Qyrus environment your key belongs to.

60-second walkthrough · No audio · Key values are hidden. The steps are also written here.

  1. Sign in to your Qyrus environment and open your profile.
  2. Go to User Token and choose Generate Token.
  3. Name the token, choose the MCP scope, and select the service permissions your tasks need.
  4. Set an expiry date and generate the token.
  5. Copy the key into your private credentials file before closing the dialog.

Keep the key in a file on your machine

Create credentials.env outside your repository and plugin folder. Replace the placeholders with your key and Qyrus application URL, then share only the file path with your agent.

Setup derives the matching MCP endpoint automatically. Your Qyrus URL is separate from the website you want to test.

X-API-Key=<your-xapi-key>
QYRION_APP_URL=https://stg.qyrus.com
Suggested locations
macOS / Linux: ~/.config/qyrus/credentials.env
Windows: %USERPROFILE%\.config\qyrus\credentials.env

Use your own environment URL. Never paste the key into chat or commit it to Git. Credential details ↗

Describe the outcome you need.

Give your agent the target environment, relevant work item or code change, and the scope it can act within.

Validate a story

Read the story I provide from my connected work tracker. Validate its acceptance criteria against my staging website and return a report with test evidence.

Reproduce a bug

Reproduce this bug on the app build and device I specify. Find the smallest failing flow and collect screenshots and session evidence.

Test a code change

Review my code diff, identify the affected user journeys, and propose the smallest useful regression set. Run the agreed checks in my test environment.

Build reusable coverage

Explore the web flow I specify, create a reusable Qyrus test, and rerun it. Report the result with evidence and any remaining coverage gaps.

Connected work trackers need their own authentication. Updating tickets or other external records follows the scope you authorize.

Access is not authority

A connection lets the agent read. Commenting, transitioning, publishing, and deleting each need your authorization.

A pass decides nothing by itself

A passing run does not close a bug, merge a change, or deploy.

Nothing runs behind your back

The plugin is not a scheduler or a background service. Work starts when you ask.

A few useful details

Before your first run

Does setup install the Qyrion CLI?

Yes. The setup skill checks Python, uv, and Qyrion and installs missing prerequisites. It uses the newest published Qyrion release for your platform, including betas, and preserves a working existing installation. It also prepares qyrusai in an isolated Python environment.

Which platforms can I use?

The Qyrion release provides macOS Apple Silicon, Linux x64, and Windows x64 binaries. Start setup in your coding-agent host; it reports any host permission or installation blocker.

View the published releases ↗

Do I need to enter an MCP URL?

No. Setup derives it from your Qyrus application URL: stg.qyrus.com uses stg-mcp.qyrus.com/mcp, and app.qyrus.com uses app-mcp.qyrus.com/mcp. The key must have access to that environment and the services you use.

Can it work from Jira, Linear, or another tracker?

Yes, when your agent has a working connector and access to the relevant work items. The Qyrus key authenticates Qyrus services; your work-management connection is separate. Ask explicitly when you want evidence written back to an issue.

Will it run in the background on its own?

The plugin gives your agent tools and workflows. Start a task in the agent, or use a scheduler supported by your host. Installing the plugin does not start an independent background service.
